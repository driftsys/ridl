## 1. What exists today

- A licence header in a `.typl`, `.ridl` or `.rsdl` file is an ordinary `//`
  comment. The lexer keeps it as trivia; it never reaches the IR.
- `ridlc` writes a marker as the first line of the two crate files of a Rust
  emit: `// Generated by ridlc. Do not edit.` in `lib.rs` and
  `# Generated by ridlc. Do not edit.` in `Cargo.toml` (`LIB_RS_MARKER` and
  `CARGO_TOML_MARKER` in `crates/ridlc/src/lib.rs`). The marker is also an
  ownership check: a build refuses to overwrite a `lib.rs` or `Cargo.toml` that
  does not begin with it (`crate_file_refusals`).
- The per-package files carry no marker. `veh.cabin.rs` begins with the first
  item's doc comment; the proto output begins with `syntax = "proto3";`; the
  FlatBuffers output begins with `namespace …;`. The TypeScript output and
  plugin output carry none either.
- The generated Rust crate carries no crate-level lint attributes. Individual
  items carry narrow `#[allow(...)]` attributes (`deprecated`, `dead_code`,
  `non_upper_case_globals`). `just demo` runs clippy with `-D warnings` over the
  cabin consumer, which reaches the generated crate.

## 2. What the ecosystem provides

There is no official, tool-wide way to mark a Rust file as generated. Each tool
does something different:

| Tool            | Behaviour                                                                                                                                                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| rustfmt         | Looks for an `@generated` comment in the first 5 lines (`generated_marker_line_search_limit`). It skips the file only when `format_generated_files = false`; the default is `true`, and both options are unstable (rust-lang/rustfmt#5080). |
| rustc, clippy   | Look for no marker. Lint attributes are the only control.                                                                                                                                                                                   |
| GitHub linguist | Recognises no Rust marker and does not look for `@generated`. A `.gitattributes` line `path/** linguist-generated=true` collapses the diff.                                                                                                 |

`@generated` is therefore the de facto token: it is what rustfmt reads, and
other tools (Phabricator, tooling at Meta) read it too.

## 3. Decisions

**H-1. Source licence headers are plain comments. No language feature.** A
header is a `//` comment block at the top of the file. It is not a doc comment
and not an attribute. Checked on 2026-10-06 with `ridl fmt` built from `main` at
7fe24437, on a `.typl`, a `.ridl` and a `.rsdl` file: the formatter keeps every
line of a leading comment block, with or without a blank line before `package`,
and keeps a comment between `package` and a doc comment. The only change it
makes is to remove trailing whitespace at the end of a line. A test that pins
this behaviour is part of the plan.

**H-2. Source comments are not copied into generated code.** Reasons:

- One generated file can draw from several source files and imported packages
  with different licences. Choosing or merging headers is a legal decision, not
  a compiler decision.
- Copying needs the IR to carry comments, and then the plugin request carries
  them to every plugin (ADR-0020). That is new surface for a value most projects
  set once.
- The licence of generated code is chosen by the person who runs the generator,
  who is not always the author of the source — for example a remote package from
  `[imports]`.

**H-3. Every generated file begins with a marker that contains `@generated`.**
Proposed text, in each target's line-comment syntax:

```text
@generated by ridl from package <pkg.Name>. Do not edit.
```

- No timestamp and no tool version, so that the output is byte-reproducible and
  a toolchain upgrade does not change every generated file. (Decided as Q-1.)
- One marker per file, including the per-package files, the TypeScript output,
  the proto and FlatBuffers output.
- The `lib.rs` and `Cargo.toml` markers change to the new text. The ownership
  check accepts both the old and the new marker, so an output directory written
  by an earlier release can still be regenerated.

**H-4. The generated Rust crate root carries a narrow lint allow list.**
`lib.rs` begins, after the header, with an inner attribute such as
`#![allow(clippy::all, missing_docs)]`. The exact list is decided during the
implementation, from what clippy reports on the cabin crate. A blanket
`#![allow(warnings)]` is rejected: it would hide real defects in what the
backend emits. A separate gate runs clippy on the generated cabin crate with the
allow list removed, so backend output quality stays checked. Single-file mode
writes no `lib.rs`, so a consumer that uses `include!` puts the `#[allow(...)]`
on the wrapping `mod` (an inner attribute is rejected inside an `include!`d
file); the book says so.

**H-5. TypeScript output also carries `/* eslint-disable */`** after the marker.
The proto and FlatBuffers output carry the marker only.

**H-6. An optional project header, set in the manifest.** A new manifest key
names a text file whose content is placed before the marker in every generated
file, one line at a time, in the target's line-comment syntax. The spelling was
decided as Q-2:

```toml
[codegen]
header-file = "LICENSE-HEADER.txt"
```

- The path is relative to the manifest. A missing file is an error diagnostic.
- In a workspace, the root's manifest is the one read, as for `[lints]`.
- The header text and the marker fields go into the codegen request, so an
  in-tree backend and a plugin render them in the same way. The host cannot
  render them in `write_response`, because only the backend knows its target's
  comment syntax.

**H-7. The book recommends a `.gitattributes` line** (`linguist-generated=true`)
for a repository that commits generated code. `ridl build` does not write it: it
is the consumer's repository.

## 4. Questions decided

Decided 2026-10-06 by Sebastien:

- **Q-1. The marker carries no `ridl` version.** With a version in it, every
  release would change every generated file, so a consumer that commits
  generated code would see a diff of every file on each upgrade. Without it, a
  release that changes nothing in the output produces no diff. The generated
  `Cargo.toml` already declares the `ridl-rt` version, which tells a reader
  which release line produced the crate.
- **Q-2. The manifest key is `[codegen] header-file`.** The setting applies only
  to generated code. A `[build]` table would suggest that it also affects
  `ridl check` or the IR dumps, which it does not.
- **Q-3. A plugin is not required to emit the marker.** The plugin protocol
  documentation recommends it, and `write_response` does not check for it.

## 6. Alternatives considered

- **Copy each source file's leading comment into the files it produces.**
  Rejected by H-2: unclear when several sources produce one file, and it puts
  comments in the IR.
- **Copy only `SPDX-License-Identifier` lines, as the set gathered from every
  contributing source.** Mechanical and avoids guessing, but still needs the IR
  and the request to carry them. Deferred until a user has a compliance
  requirement for it.
- **A licence attribute in the language** (`@license("MIT")` on a package).
  Rejected: an asymmetry between generated targets does not justify new syntax,
  and an attribute does not cover a copyright line.
- **`#![allow(warnings)]` on the generated crate.** Rejected by H-4: it hides
  defects in the backend's output.
- **The Go convention, `// Code generated … DO NOT EDIT.`** Linguist recognises
  it only for Go files, and rustfmt does not read it. `@generated` is the token
  the Rust tools read.
