# The generated interaction face v0 — design (Lane M, stage M1)

Working memory for Lane M, the MVP of the generated `Client`/`Provider`/
`dispatch` face over `ridl-rt`. The lane and its stages are
[`2026-09-15-lane-m-driver.md`](./2026-09-15-lane-m-driver.md). This document
settles what M2 plans and M3 builds. Archive it with the plan when the lane's
last stage lands, per `sdd-gardening`.

**Status: every decision below was taken on delegated authority.** Sebastien
delegated the decisions for this session rather than answering them one at a
time, so this is not the section-by-section brainstorming the driver prompt
describes. Each decision states its reasoning and its alternatives so it can be
read and overturned. §11 lists the four that most deserve a second opinion. The
stage does not merge until Sebastien has approved the written spec.

## 1. Scope

The MVP generates, for one example ridl package, the consumer and provider faces
of one interface, and proves them with an in-process round trip in a test. It is
in-process only.

**In scope.** The interface and interaction descriptors of
`crates/ridl-rt/src/contract.rs`; a `Client` generic over exactly the ports its
interface needs; a `Publisher` over the writer ports; a `Provider` trait the
application implements; a generated `dispatch` that routes a claim by ordinal,
decodes arguments, evaluates `require`, calls the provider and settles.

**Out of scope, and why that is safe for an MVP.**

| Excluded                                            | Why the MVP does not need it                                                                                                                                                                                                |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E11.1, the frame specification                      | A frame is how two processes agree on bytes on a wire. Both halves of this round trip are in one process and exchange `&[u8]` through the placeholder ports of §5, so no frame exists to disagree about.                    |
| E11.9, `ridl-transport-ws` and the loopback runtime | The face binds port traits, not a runtime. Any implementation of those traits drives it, and §5 supplies a test-only one. When E11.9 lands, the same generated code runs against it unchanged — that is the point of RA-19. |
| E11.7, E11.8, E11.12, the three codecs              | The generated face is generic over `T: Payload<E>` and never names an encoding's internals. It does not care who wrote the `Payload` impl, so §2 supplies one by hand for the example package's types.                      |
| Signals' `ScannableSignals` and `CoherentSignals`   | Both are extensions a runtime may omit (`port.rs:13`). A coherent multi-read is a separate generated method bounded on `CoherentSignals` (design note §8), which the MVP does not emit.                                     |
| Every language backend but Rust                     | ADR-0020 decision 7 gives TypeScript the same three layers. Proving the shape once in Rust is what tells us the shape is right.                                                                                             |

The risk this scope carries is that the face is shown to work only against ports
we wrote ourselves. That is the known cost of starting before E11.9, and it is
why §5 insists the placeholder stays disposable.

## 2. The payload encoding: `ReprC`, with hand-written impls, generated by nobody

**Decision. The MVP generates no codec.** The example package's types get a
hand-written `Payload<ReprC>` implementation that lives in the test, is marked
throwaway in its own module documentation, and is deleted when E11.12 lands.

ADR-0020 decision 1 sanctions exactly three encodings, and none of the three is
built. The driver prompt allows either the cheapest path to something real or a
narrowly scoped stand-in. This is the second, drawn as narrowly as it can be
drawn, and the reason it can be this narrow is worth stating plainly: **the
generated face is generic over `T: Payload<E>` and calls only `Ref::encode`,
`Ref::verify` and `Ref::decode`.** It never sees a field, a tag or a layout. So
whether the `Payload` impl is generated or hand-written changes nothing about
the code M3 generates — it changes only who supplies a trait impl the example
package needs in order to compile.

`ReprC` is the marker, for two reasons: of the three it is the one whose
hand-written stand-in needs no dependency and no schema, and it is the one whose
real codec (E11.12) will replace the stand-in with the least disturbance,
because the encoding's own shape is a fixed layout either way.

The stand-in covers only what the example package of §7 uses: fixed-width
scalars, an enum, and structs whose fields are all fixed-size. It is not a
subset anyone should build on. It carries no optional field, no sequence, no map
and no union, and M3 must not extend it to acquire one — a type the stand-in
cannot carry is a reason to simplify the example package, not to grow the
stand-in.

**Alternative rejected: generate `Payload<ReprC>` for a restricted type
subset.** This is more real, and it is a down-payment on E11.12 rather than a
throwaway. It was rejected because it pre-empts an epic whose design is not
written: the layout struct, the emitted C header, and the removal of
`#[repr(C)]` from the generated domain structs are all E11.12's, and a partial
answer generated now would have to be reconciled with them. The MVP's question
is whether the face is right, and a generated codec does not help answer it.

## 3. Interface numbering: the IR's provisional number, unchanged

**Decision. The example package carries no `interfaces.lock`, and the emitter
reads `Interface.number` and `Interface.provisional` straight from the IR.**

The driver prompt told M1 to re-check `origin/main` here, because this section
was overtaken once by a concurrent merge. It was re-checked at `d2e9d41`, which
is `origin/main`'s head as this was written, and the section now holds:

- `crates/ridl-ir/proto/ridl/ir/v2/ir.proto` carries `Interface.number` (field
  7) and `Interface.provisional` (field 8), added by #391 (`fdcf2ca`).
- `crates/ridl-rt/src/contract.rs` already declares `Interface::NUMBER` and
  `Interface::PROVISIONAL`, so the descriptor has somewhere to put both.
- Nothing merged between `fdcf2ca` and `d2e9d41` touches either. Lane L's L4 is
  the last change in this area.

A provisional number is correct for this MVP. RIDL-411 blocks _publishing_ a
provisional number, not using one; nothing in this lane publishes. The example
package gets its number for free at compile time, and `PROVISIONAL` is emitted
as `true`, which is an honest statement rather than a placeholder.

## 4. The catalog hash: a zero placeholder, tied to E16.2

**This decision is not on the driver prompt's list.** It was found while reading
`contract.rs` and it blocks M3, so it is settled here.

`Interface::CATALOG` is a `&'static CatalogRef`, and a `CatalogRef` is a package
name plus a `CatalogHash([u8; 32])`. That hash is SHA-256 over the reachable
closure, and **it is not built**: it is story E16.2, open as driftsys/ridl#378,
and its design is `docs/wip/2026-09-13-runtime-descriptors-design.md`. The
driver document's dependency section does not mention it.

**Decision. The emitter writes `CatalogHash([0u8; 32])` and says in the
generated doc comment that the hash is a placeholder until E16.2.**

This is safe for exactly this MVP, for a reason that stops holding the moment
the MVP does: `CatalogRef` compares equal only when both the name and the hash
are equal (`contract.rs:27-29`), so with one package in one process the name
alone still separates catalogs, and a hash that is constant across every package
cannot cause two different catalogs to be mistaken for each other **while only
one exists**. With two packages present, two zero hashes would compare equal
whenever the names did, which is precisely the confusion the hash exists to
prevent. M3 therefore keeps the example package to one catalog, and E16.2
replaces the zero before a second one appears.

An alternative — hashing something cheap and local, such as the package name —
was rejected because it would put a second, wrong definition of the catalog hash
into the tree, and a wrong hash that looks computed is worse than a zero that
obviously is not.

## 5. The placeholder ports: test-only, one file, disposable

**Decision. M3 writes an in-process implementation of the port traits as a
test-support module inside the Rust backend's test tree, not as a crate.**

`ridl-rt` ships no runtime; the first real one is E11.9's `ridl-loopback`
(ADR-0020 decision 6). The placeholder exists only so the round trip of §7 has
something to run against.

- **Where.** `crates/ridl-backend-rust/tests/support/loopback.rs`, reached only
  from that crate's tests. Not a crate, not a `[dev-dependencies]` entry any
  other crate can reach, and not published. Making it a crate is how a throwaway
  becomes permanent.
- **What.** `SignalReader`, `SignalWriter`, `EventSource`, `EventSink`,
  `Caller`, `Handler`, `FixedReader`, `Clock` and `Attached`, over a map from
  `(InterfaceNo, Ordinal)` to a byte vector for signals and `fixed`, and a queue
  per ordinal for events and calls. No IO, no thread, no real time — the `Clock`
  returns a counter the test advances by hand.
- **What it must not become.** It implements neither `ScannableSignals` nor
  `CoherentSignals`. Omitting them is allowed (`port.rs:13`) and it keeps the
  placeholder from drifting toward being the reference runtime, which is E11.9's
  job and carries E11.9's design.
- **How it is retired.** The M3 pull request's description names E11.9 as its
  replacement, and the module's own documentation says so too, so the person who
  lands E11.9 finds the instruction rather than having to infer it.

The one property it must get right is the one the face depends on: `Caller` and
`Handler` are two ends of the same queue, so a command sent through `Caller`
must appear at `Handler::next_claim`, and the settlement must come back to
`Caller::ack` or `Caller::reply`. Everything else about it can be naive.

## 6. The generated shape

The shape is the design note's §8 (`2026-09-08-ridl-rt-design.md:770-839`),
adapted by §2, §3 and §4 above and reduced to the MVP's scope. For the example
package's interface the emitter writes one module holding:

- a unit struct per interface with `impl Interface`, carrying `CATALOG`,
  `NUMBER`, `PROVISIONAL`, `NAME` and `MEMBERS`;
- a unit struct per interaction with `impl Interaction` plus the kind's trait —
  `Signal`, `Event`, `Command`, `Query` or `Fixed` — carrying the payload or
  argument and reply types, `init()` for a signal, and `require()` for a command
  or a query;
- `Client<'a, P>`, generic over exactly the ports the interface's interactions
  need and no others, with one method per consumer-side interaction;
- `Publisher<'a, W>` over `SignalWriter + EventSink`, with one method per
  provider-side signal and event, plus `invalidate_*` and `commit`;
- `trait Provider` with one method per command and query;
- `fn dispatch<H: Handler, P: Provider>(h: &mut H, p: &mut P, buf: &mut [u8]) -> usize`.

**RA-19 holds.** The port bounds on `Client` are computed from the interaction
kinds the interface actually declares: an interface with no query and no command
produces a `Client` with no `Caller` bound. This is a property M3 tests
directly, with an interface of each shape, not something it asserts in prose.

**RA-20 holds.** Generated code contains no thread, future, socket or timer. A
query returns a `Correlation` and a separate `*_reply` method polls it; nothing
in the generated file waits. `dispatch` is a single pass over the claims that
are ready and returns how many it settled — the loop that calls it is the
application's or the runtime's.

Two reductions from §8, both following from §1: no method is bounded on
`CoherentSignals`, and `ensure` is not evaluated. `require` is, because
`contract.rs` already declares it on `Command` and `Query` and the dispatch has
to call something before the provider runs. `ensure` needs the reply in hand and
a place to put the failure, and the MVP settles `Contract::PreconditionFailed`
from `require` only. M2 records `ensure` as a follow-up, not as a silent gap.

## 7. Where the code is generated from, and where the round trip lives

**The emitter.** A new module in `crates/ridl-backend-rust`, not a new crate.
The face is the same backend's phase 2 (ADR-0018 decision 15), and a second
crate would split one backend's output across two.

- `crates/ridl-backend-rust/src/descriptors.rs` — the `Interface` and
  interaction descriptor impls.
- `crates/ridl-backend-rust/src/face.rs` — `Client`, `Publisher`, `Provider` and
  `dispatch`.
- `crates/ridl-backend-rust/src/lib.rs` — two module declarations and the call
  that appends the new items to what `generate` already returns. §9 covers the
  collision this creates.

The backend gains `ridl-rt` as a `[dev-dependencies]` entry only, because the
backend emits text that links `ridl-rt` and does not itself link it; the test
that compiles the emitted text needs it.

**The example package.** A single-file ridl package in
`crates/ridl-backend-rust/tests/fixtures/`, modelled on
`crates/ridl-backend-proto/tests/fixtures/cruise.ridl` but cut down to what §2's
stand-in can carry: fixed-width named scalars, one enum, one struct of those,
and one interface declaring one signal, one event, one command and one query.
One of every kind the descriptors cover except `fixed`, which M2 may add if it
costs nothing.

**The round trip.** A test in `crates/ridl-backend-rust/tests/` that compiles
the generated face together with the placeholder ports of §5 and the hand-
written `Payload<ReprC>` impls of §2, then: publishes a signal and reads it back
through `Client`, raises an event and receives it, and sends a command and a
query through `Client`, runs `dispatch` against a `Provider`, and observes the
acknowledgment and the reply. **That test passing is M3's done-when.** Note that
the generated code must be compiled, not just snapshotted — a snapshot test
would have told us nothing, and "has never been compiled" is the exact complaint
ADR-0018's Alternatives table made about the retracted layer.

## 8. The coupling to Lane C's Epic 10 — accepted rework

Epic 10 is reshaping the Rust types this face uses as argument and return types,
in the same file this lane extends (the lanes plan's P-5: Task 6 changes struct
and union declarations, Task 3 changes named-scalar emission). Lane M starts
before Lane C lands.

**This is accepted rework, not a blocker.** The face's methods name those types
but do not depend on their internals, so what changes is the generated text the
round-trip test compiles, and the hand-written `Payload<ReprC>` impls of §2 that
construct values of them. The cost is one touch-up pass after Epic 10 lands,
paid by whoever lands Epic 10's Task 3 or Task 6 and finds the backend's tests
red. M2 names this in its own risk list so the plan carries it, and the M3 pull
request description says it out loud.

Accepting it is a judgement that the face's shape is worth learning now rather
than after Epic 10, at 0.x, where a touch-up pass is cheap. If Epic 10 lands
before M3 starts, the cost disappears and nothing about this spec changes.

## 10. Alternatives considered

| Alternative                                                  | Why not                                                                                                                                                                                                               |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wait for E11.1 and E11.9, as ADR-0018 decision 15 sequences  | That is the correct order and this lane is a deliberate exception to it. The team has nothing to write against today, and the face's shape is the thing most worth learning early, because every later epic binds it. |
| Generate a `Payload<ReprC>` codec for a restricted subset    | Pre-empts E11.12, whose layout struct and C header are unwritten. See §2.                                                                                                                                             |
| Invent a fourth encoding, or a JSON stand-in                 | ADR-0020 decision 1 closes the set and `Encoding` is sealed, so it is not expressible without changing `ridl-rt`. Correctly impossible.                                                                               |
| Put the placeholder ports in a new `ridl-loopback` crate now | That is E11.9's name and E11.9's design. Taking the name now would either constrain that story or force a rename. See §5.                                                                                             |
| Put the face in a new crate beside `ridl-backend-rust`       | The face is the same backend's phase 2. Two crates would split one backend's output and give the plugin system of ADR-0020 decision 9 two things to invoke instead of one.                                            |
| Snapshot the generated face instead of compiling it          | "It cannot be connected to a runtime at all, and has never been compiled" is what ADR-0018 said about the retracted layer. Repeating it would reproduce the defect.                                                   |
| Hash the package name into the catalog hash                  | A wrong hash that looks computed is worse than a zero that obviously is not. See §4.                                                                                                                                  |

## 11. What Sebastien should look at first

Every decision here was taken without him. These four carry the most judgement:

1. **§2, no generated codec.** The MVP proves the face and not the encoding. If
   the point of the MVP is for the team to write real payloads against it, this
   is the wrong call and §2's rejected alternative is the right one.
2. **§4, the zero catalog hash.** This dependency was not in the driver
   document. If E16.2 is closer than it looks, waiting for it is cheaper than
   placing a placeholder that §4 admits stops being safe at two packages.
3. **§6, `ensure` not evaluated.** A deliberate reduction. It makes the MVP's
   provider side incomplete against ridl §6 and §7.
4. **§9, E11.13 and the `docs/ROADMAP.md` ordering.** The identifier is
   mechanical and checked; whether M1 may edit the roadmap before B2 is a
   coordination call.
