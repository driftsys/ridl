# Release 0.10 — lanes plan

**Spec:**
[`2026-10-11-release-0.10-design.md`](2026-10-11-release-0.10-design.md). Read
it first. This plan does not repeat its decisions (R-1 to R-9); it says who does
what, in which order, and what each lane's session starts from.

The spec covers seven independent lanes, so there is no single task-by-task
plan. Lane 0's task plan is
[`2026-10-11-freeze-check-plan.md`](2026-10-11-freeze-check-plan.md). Every
other lane writes its own design (where one is needed) and its own task plan in
its own session, from the brief in section 4, and executes it with
subagent-driven development and the per-task review gate.

## 1. Rules for every lane

1. One session per lane, one worktree per lane, created from `origin/main` under
   `.claude/worktrees/`. Run `./bootstrap` in it.
2. Claim an issue with a comment ("Claimed by lane X for release 0.10") before
   you start it. Do not start an issue that another lane has claimed.
3. One pull request per issue or per tightly coupled group of issues. Run
   `/review` passes 1 and 2 before asking for a merge. Sebastien merges; an
   agent never merges without his explicit "merge".
4. A breaking change before 0.10.0 carries `!` in its title. If the surface's
   gate is already on, a pull request that moves that surface's `baseline` in
   `freeze/surfaces.toml` to the break's merge commit follows it; until it
   merges, `main` fails `freeze-check`, so merge the two back to back (spec
   4.4).
5. Every surface already has its dump under `freeze/` (lane 0 builds them all),
   and `just freeze-check` fails when a change to a surface is not committed to
   its dump, so every change to a surface shows in the diff. When the last
   pending break of a surface merges, the lane opens a one-line pull request
   that adds that surface's row to `freeze/surfaces.toml`, with that merge
   commit as `baseline` (section 3). The row cannot go in the same pull request,
   because its baseline must be a commit on `main`.
6. Each breaking change gets a heads-up issue on driftsys/ridlc-gen-kotlin,
   linked from the pull request.
7. When a lane finishes or a session ends, record the lane's state in a memory
   file named `release-0-10-lane-<x>-state.md`.
8. Delegated rulings are recorded in the pull request body as `R-<lane>-<n>` and
   reported to Sebastien at the end of the lane.

### Lane W — wire and runtime

You own the frame specification, `ridl-rt`, `ridl-rt-conformance`,
`ridl-loopback` (except the `Loopback<E>` change, which is 1b in lane C) and
`ridl-descriptor`. Order:

1. The WebSocket binding document: the frame specification §11.1 amendment, the
   ruling on §6.1 against the `attach` hash (see lane H's record in
   `docs/design/catalog-descriptor.md`), items 5 and 12 of #350, the header and
   envelope sizes that #718 records. This is design work: brainstorm it with
   Sebastien.
2. The other open items of #350, #855, a ruling on #802, and a ruling on #336
   that streams arrive in 0.11 as an addition.
3. #858: one source for the encoding names and the cargo feature names.
4. Review the `.proto` and `.fbs` output of the backends against the corpus, so
   that #264 can ship without changing it. Record the result in ADR-0019 or
   ADR-0016.
5. The frame specification drops "Draft".
6. Minimum Rust version (spec 5.3 step 6): `ridl-loopback` and `ridl-descriptor`
   at edition 2021 and `rust-version = "1.83"`, or a stated other minimum;
   `just compat-check` builds the published manifests as they are, and the
   veh-cluster generated crate at the minimum with every codec feature on.

You switch on `runtime-crates`, `wire` and `msrv`.
